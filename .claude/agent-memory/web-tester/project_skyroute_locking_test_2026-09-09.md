Tested the "lock waypoints during building growth" feature (scenarios A-D from the test brief) on 2026-09-09. Score given: 62/100. Full report delivered in chat; key durable facts below.

**Stack**: packages/backend (Express + better-sqlite3, tsx watch, port from .env PORT=3001) + packages/frontend (Vite + React + Mapbox GL, port 5173 or next free e.g. 5174). Local `.env` at repo root has fake Mapbox token by design — tile/geocoding 401s are expected noise, not bugs. Mission draft autosaves to localStorage key `droneroute_draft_v1` (readable/writable directly — useful shortcut for inspecting exact building vertex lat/lng instead of eyeballing screen pixels).

**Confirmed working**: lock/unlock UI is fully correct — amber left border + amber lock icon on locked rows, bulk toolbar button toggles label/color (Zamknout↔Odemknout, text-amber-400), per-row lock toggle affects only that row, orbit-template generation from a drawn building works, building creation (rectangle draw via mouse drag) works.

**Bug found (reproducible, DOM-measured, not a guess)**: the bottom action bar for multi-selected waypoints (and very likely the sibling "Budova změněna" recalculation bar — same component family) overflows horizontally at 375px viewport with no wrap/scroll. Measured via getBoundingClientRect at innerWidth=375: "Zrušit výběr" (X) button at x=534-555 and "Smazat" at x=428-509 — both fully off-screen; "Upravit šablonu" right edge at x=404, clipped. Only the leftmost 1-2 buttons (lock toggle, start of "Upravit") are reachable by tap on a real 375px phone.

**Untested / could not verify — "Budova změněna" recalculation flow (Scenario B)**: could not get either the building-polygon click (to open the height popup) or the building-vertex drag (to trigger resize) to register through any automation method tried: raw synthetic MouseEvent dispatch on canvas/marker/document/window (with and without hover-priming), CDP-level `drag` tool (chrome-devtools-mcp) both directly on real interactive marker elements (pointer-events:auto, uid-based) and via invisible pass-through overlay proxies (pointer-events:none) positioned at exact `map.project()`-computed pixel coordinates. Confirmed the coordinates themselves were correct (matched localStorage vertex data projected through the live Mapbox instance). One waypoint-marker drag (point 12, unlocked) DID appear to succeed once via the CDP `drag` tool, with the position change only becoming visible after a later unrelated click (debounced state commit) — so dragging is _possible_ in principle but highly unreliable to trigger via this toolchain. **Recommend a follow-up session drive this with a real Playwright/CDP mouse press-move-release sequence with realistic per-frame movement (not 2-3 jump points) and generous settle delays, or just have a human do one manual pass through Scenario B.**

**Automation gotchas learned this session** (for future SkyRoute testing):

- Map building/waypoint label overlays (`.mapboxgl-marker` divs) are mostly `pointer-events:none` (pure visual labels) — the actual interactive layer for click/drag is a Mapbox GL canvas render layer (queryRenderedFeatures), reached via `.mapboxgl-canvas`. New-shape drawing (rectangle/polygon tool) responds fine to synthetic `mousedown/mousemove/mouseup` dispatched straight on `.mapboxgl-canvas`; existing-feature click-select and vertex/marker drag do not respond reliably to synthetic dispatch — needs real trusted input.
- The chrome-devtools-mcp `drag` tool can leave Playwright's internal mouse-button state stuck "pressed" if it errors mid-drag (e.g. source element fails an actionability check) — a subsequent `click`/`drag` call then throws `'left' is already pressed`. Recovery: `click` on any normal, fully-visible, pointer-events:auto button resets it.
- The React Fiber tree holds the live Mapbox `Map` instance reachable via `container.__reactFiber$xxx` → walk `.return` chain checking each fiber's hook linked-list (`memoizedState` → `.next`) for a ref whose `.current.queryRenderedFeatures` is a function. Useful for `map.project([lng,lat])` to get ground-truth pixel coordinates instead of guessing from screenshots.
- Windows excluded TCP port ranges should be checked before assuming port 3001 will be blocked (see global memory note) — this run it was free (excluded ranges were 2880-2979 and 3008-3107).
